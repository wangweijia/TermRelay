# TermRelay 可行性评估

评估对象：`TermRelay_开发实现文档.md` v1.2。

## 结论

项目在技术上可行，适合按“单用户 / 少量 Mac / 可信网络”的 MVP 推进；综合可行性为 **中高（7/10）**。核心链路中的技术都成熟，但成败主要取决于阶段 0 的终端体验、网络背压，以及上线前补齐身份与授权边界。当前文档足以指导原型，不足以直接作为公网生产系统的安全设计。

建议 Go，但采用带门槛的分阶段决策：先投入阶段 0 和一个最小纵向闭环，不同时铺开审批、通知、审计和多工具适配。

## 分项判断

| 维度 | 判断 | 说明 |
| --- | --- | --- |
| Mac 原生终端 | 中高 | SwiftTerm + PTY 路线成熟；TUI、进程组和 App 生命周期需实机验证 |
| 双 WebSocket 中继 | 高 | 架构简单；必须实现背压、重连、幂等和状态快照 |
| NestJS + Vue 单镜像 | 高 | 常规构建方式；生产需验证 SPA fallback 与 WebSocket 升级 |
| JSON Schema 跨语言契约 | 高 | 合理；必须让生成和兼容性检查进入 CI |
| MySQL 持久化 | 中高 | 元数据适合；高频终端原始流不适合无限逐条入库 |
| Cloudflare 公网入口 | 中高 | Tunnel + Access 合适；应用仍需验证 Access JWT 和权限 |
| 结构化审批 | 中 | 依赖各 CLI 的稳定机器协议；纯 PTY 无法可靠推断审批语义 |
| 运维与分发 | 中 | 容器简单；macOS 签名、公证、自动更新仍是独立工作流 |

## 文档中的主要问题

### P0：进入公网或非隔离 LAN 前必须解决

1. **Mac 连接无认证。** `device_id` 只是标识，任何能访问 `/ws/client` 的主机都能冒充设备。开发期可以保留，公开试用前至少增加一次性配对后签发的设备令牌，并支持吊销。
2. **浏览器身份只依赖上游描述。** Server 必须校验 Cloudflare Access JWT 的签名、`aud`、`iss` 和有效期，并把身份写入审计，不能只信任可伪造的请求头。
3. **远程输入等价于本机代码执行。** 授权必须细化到用户、设备、工作区和动作；服务端校验后，Mac 仍需再次校验工作区授权和命令幂等。
4. **终端输出可能泄密。** 输出、提示词和命令可能包含密钥或客户数据。必须定义加密、日志脱敏、TTL、配额和删除策略。

### P1：进入完整 MVP 前解决

1. `devices.public_key` 与“不使用设备密钥”矛盾；M0 数据模型应删除该字段，若采用配对方案则改成独立 credential 表。
2. 文档提到 ACK 和补传，却没有定义 ACK、错误、状态快照、最大消息大小和兼容规则；初始化契约已补入最小 ACK/错误 Schema，其余仍需扩充。
3. “events 全量入 MySQL”会产生写放大。建议元数据与终端字节分开，终端流采用 16–64 KiB 压缩分块、短 TTL 和每会话上限。
4. 审批能力不能从 ANSI 文本可靠识别。只有工具适配器提供结构化事件时才启用审批 UI，否则只允许普通远程输入并明确风险。
5. 缺少可观测性指标：连接数、输出队列深度、丢弃字节、ACK 延迟、重连次数和命令执行耗时应进入基础监控。

## 建议的最小纵向闭环

只实现一台 Mac、一个自定义 shell 命令、一个浏览器页面：

1. Mac 本地选择已授权目录并启动 PTY。
2. PTY 输出经 20–50 ms / 16 KiB 批处理送到 Server。
3. Web 使用 xterm.js 显示，并能发送输入、resize 和 interrupt。
4. 主动断网 30 秒后重连，验证有限补传、重复命令和状态快照。
5. 用持续高速输出压测 30 分钟，确认本地终端不被网络拖慢、内存有硬上限。

这条链路通过后，再接 Codex、MySQL 历史、审批和公网入口。

## Go / No-Go 验收门槛

| 门槛 | Go 条件 |
| --- | --- |
| 终端正确性 | 中文、颜色、全屏 TUI、resize、复制和 Ctrl-C 均通过 |
| 交互延迟 | 可信 LAN 下 P95 按键回显低于 150 ms |
| 稳定性 | 30 分钟高速输出不阻塞本地 UI，内存不随断网持续增长 |
| 恢复 | 断网重连后不重复执行命令，状态最终一致 |
| 安全 | 公网试用前完成 Access JWT 校验、设备认证、授权和审计 |
| 工具抽象 | 第二种普通 CLI 接入不修改 Session 与协议核心 |

若终端探针或背压测试失败，应暂停完整 UI 和数据模块开发；若 ACP 不可用，只取消结构化审批，不影响纯 PTY MVP。

## 粗略投入

对熟悉 Swift/AppKit、Node 和 WebSocket 的 2–3 人团队：阶段 0 约 1–2 周；可演示纵向闭环约 3–5 周；达到带公网访问的可用 MVP 约 8–12 周。macOS 分发、复杂 TUI 兼容和设备认证可能使周期增加。该估算是工程判断，不是承诺，阶段 0 结束后应重新估算。
